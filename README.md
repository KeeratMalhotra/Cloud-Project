# EdgePlus-PEC

**Priority queues, energy-aware mobility, and fast ledger consensus for deadline-aware 6G edge scheduling.** A reproduction and extension of EdgePlus.

Keerat Malhotra, Bhavya Maheshwari, Bhumika Aswal

📄 **Paper:** [PDF](paper/EdgePlus-PEC.pdf) · [LaTeX source](paper/latex/main.tex) · [Overleaf project (zip)](paper/EdgePlus-PEC_overleaf.zip)

## Overview

EdgePlus (Taher et al., *IEEE Internet of Things Journal*, 2026) assigns air-quality IoT tasks in three 6G slices to stationary edge servers, mobile edge servers, and the cloud. The slices are URLLC, eMBB, and mMTC, with deadlines of 5–15 s, 30–120 s, and 120–600 s. Its scheduler is multi-agent reinforcement learning: masked cooperative PPO (CCPPO), an advisory layer, a particle-swarm outer loop, and a ledger whose reputation signals feed back into scheduling.

This project:

1. **Reproduces EdgePlus** in an open, event-driven simulator. The simulator's queueing engine matches queueing theory within 5%.
2. **Extends it as EdgePlus-PEC.** It makes three changes to the system and keeps the same scheduler:
   - **P, priority queues:** servers run URLLC before eMBB before mMTC.
   - **E, energy-aware execution and mobility:**
     - a neighbouring site's mobile server serves a task where it is parked, instead of driving over;
     - mobile servers are redeployed less often;
     - edge cores slow down when a deadline leaves room (DVFS).
   - **C, fast ledger consensus:** ledger blocks are closed within 0.5 s, and cloud BFT rounds run every 0.5 s instead of every 5 s.
3. **Evaluates both** on CityPulse, the data EdgePlus used, and on real bus-mounted sensor data from New Delhi (AirDelhi). The models are trained only on CityPulse and run on AirDelhi without retraining.

## Main results

The table shows 150,000 tasks per 10-minute episode, on held-out test days, with 3 training seeds × 5 test episodes per system.

| Metric | CityPulse: EdgePlus | CityPulse: EdgePlus-PEC | AirDelhi: EdgePlus | AirDelhi: EdgePlus-PEC |
|---|---|---|---|---|
| On-time success | 78.8% | **99.3%** | 54.9% | **76.3%** |
| URLLC on-time success | 44.1% | **100%** | 24.9% | **98.6%** |
| Energy per episode | 133.0 MJ | **0.94 MJ** | 202.7 MJ | **58.7 MJ** |
| Ledger commit delay (95th percentile) | 19.3 s | **0.50 s** | 23.6 s | **0.50 s** |

- **Paired tests.** On both datasets, all 15 paired test episodes favour EdgePlus-PEC on these four measures (Wilcoxon signed-rank test with Benjamini–Hochberg correction, q = 6.7 × 10⁻⁵).
- **Costs.** mMTC success is 2.3 percentage points lower on CityPulse and 12.5 points lower on AirDelhi. On AirDelhi, the 95th-percentile latency rises from 152 s to 308 s. The ledger uses about 10 times more CPU time.
- **Where the gain comes from.** A simple greedy earliest-finish-time rule reaches the same success as the trained scheduler on both systems, so the improvement comes from the system changes, not from learning.
- **Reproduction.** Our EdgePlus reaches 78.8% success at 150k tasks; the EdgePlus paper reports 82.77%.

All tables, with confidence intervals: [`results/summary/pec_comparison.md`](results/summary/pec_comparison.md).

## Repository layout

```
configs/            settings: simulator (sim.yaml), system presets (systems.yaml), learned methods
                    (methods.yaml), datasets, workload, topology
src/edgesim/        Python package
  data/             dataset loaders (CityPulse, AirDelhi), labelling, episode builder, data mirror
  sim/              event-driven simulator (env.py), world, radio model, metrics, calibration
  agents/           rule-based dispatchers, CCPPO learner, features, rewards, advisory layer, PSO
  runner.py, experiments.py, topology.py, plots.py, config.py
scripts/            command-line entry points (listed below)
results/summary/    the result files behind every table and figure in the paper
docs/Simulator.md   simulator specification, validation, calibration, rule-based baselines
docs/figures/       figures generated by the scripts
paper/              the paper: PDF, LaTeX source, Overleaf zip
```

The repository has three branches:

| Branch | Content |
|---|---|
| `main` | Code, results, and the paper |
| `data-mirror` | Parquet copies of both datasets with SHA-256 checksums |
| `runs-mirror` | Trained checkpoints, training logs, and evaluation results |

## Setup

You need Python 3.10 or newer; we used 3.11. No GPU is needed.

```bash
git clone https://github.com/KeeratMalhotra/Cloud-Project.git
cd Cloud-Project
uv venv -p 3.11 .venv                      # or: python3 -m venv .venv
uv pip install --python .venv/bin/python -e .
uv pip install --python .venv/bin/python torch --index-url https://download.pytorch.org/whl/cpu
uv pip install --python .venv/bin/python cryptography tabulate   # crypto timings; status tables
```

With plain pip, replace `uv pip install --python .venv/bin/python` with `.venv/bin/pip install`.

## Data

```bash
.venv/bin/python scripts/download_data.py --dataset citypulse    # from the data-mirror branch
.venv/bin/python scripts/download_data.py --dataset airdelhi
.venv/bin/python scripts/prepare_data.py --dataset citypulse     # labels, sites, figures (about 15 s)
.venv/bin/python scripts/prepare_data.py --dataset airdelhi      # (about 25 s)
```

| Dataset | Content |
|---|---|
| CityPulse | 449 sites, 1 Aug to 1 Oct 2014, readings every 5 minutes, 7.9M readings. Generated data located in Aarhus, Denmark. |
| AirDelhi | Particulate-matter sensors on 13 public buses in New Delhi, 1 Nov 2020 to 30 Jan 2021, 12.5M real readings. |

Both datasets are split by day into training, validation, and test days. To rebuild the mirror from the original sources, use `--source original`, then `scripts/build_data_mirror.py`.

## Reproducing the results

### From the trained runs (a few minutes)

```bash
bash scripts/sync_runs.sh pull             # trained checkpoints and evaluations from runs-mirror
.venv/bin/python scripts/status.py         # list the runs and their saved results
.venv/bin/python scripts/compare.py        # Tables IX-XI and Fig. 4 of the paper
```

### From scratch

| Paper item | Command |
|---|---|
| Table I (crypto costs) | `scripts/bench_crypto.py` |
| Table III (simulator vs queueing theory) | `scripts/validate_simulator.py` |
| Fig. 3 (capacity calibration) | `scripts/calibrate_capacity.py --dataset citypulse` |
| Table IV (rule-based dispatchers) | `scripts/run_heuristics.py --dataset citypulse --split test`, then the same with `--dataset airdelhi` |
| Training (Section VIII) | `scripts/launch.py`, see below |
| Tables IX–XII, Fig. 4 | `scripts/evaluate.py`, then `scripts/run_heuristics.py ... --tag _pec`, then `scripts/compare.py`, see below |

Table IV was computed with reputation updated instantly at task completion (`ledger.consensus.mode: instant` in `configs/sim.yaml`). With the default timed ledger the numbers move slightly; for example, greedy EFT at 150k on CityPulse gets 79.9% instead of 80.6%.

**Training.** Nine runs, 1.5M decisions each, with the methods in `configs/methods.yaml`:

```bash
.venv/bin/python scripts/launch.py --minutes 60 -- \
  "--method edgeplus --seed 0" "--method edgeplus --seed 1" "--method edgeplus --seed 2" \
  "--method edgeplus_pec --seed 0" "--method edgeplus_pec --seed 1" "--method edgeplus_pec --seed 2" \
  "--method edgeplus_pq --seed 0" "--method edgeplus_energy --seed 0" "--method edgeplus_cons --seed 0"
```

- Training is resumable. Rerun the same command if it stops early; `scripts/status.py` shows the progress.
- On an 8-thread CPU, the nine runs take about 55 minutes in parallel.

**Evaluation and statistics:**

```bash
RUNS="runs/citypulse/edgeplus_s0 runs/citypulse/edgeplus_s1 runs/citypulse/edgeplus_s2 \
      runs/citypulse/edgeplus_pec_s0 runs/citypulse/edgeplus_pec_s1 runs/citypulse/edgeplus_pec_s2 \
      runs/citypulse/edgeplus_pq_s0 runs/citypulse/edgeplus_energy_s0 runs/citypulse/edgeplus_cons_s0"
SYSTEMS="edgeplus edgeplus_pec edgeplus_pq edgeplus_energy edgeplus_cons"
.venv/bin/python scripts/evaluate.py --minutes 60 --workers 8 --split test --regimes stress --seeds 0 1 2 3 4 --runs $RUNS
.venv/bin/python scripts/evaluate.py --minutes 60 --workers 8 --dataset airdelhi --split test --regimes stress --seeds 0 1 2 3 4 --runs $RUNS
.venv/bin/python scripts/run_heuristics.py --dataset citypulse --split test --policies greedy_eft --regimes stress medium --systems $SYSTEMS --tag _pec
.venv/bin/python scripts/run_heuristics.py --dataset airdelhi --split test --policies greedy_eft --regimes stress --systems $SYSTEMS --tag _pec
.venv/bin/python scripts/compare.py
```

- Each evaluation call (45 episodes per dataset) takes about 8 minutes with 8 workers.
- Already-saved episodes are skipped, so an interrupted call can be rerun.

The protocol-study runs in Tables V–VI of the paper are also on `runs-mirror`. They were produced by an earlier version of the code, from before the timed ledger was added.
